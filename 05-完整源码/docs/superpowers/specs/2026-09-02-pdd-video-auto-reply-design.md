# 拼多多客户视频自动回复设计

## 目标

当未读会话中的客户发送视频时，正式客服程序在同一个 UI 租约内识别视频、自动打开预览、从拼多多 CEF 新增缓存记录取得临时视频地址、下载并校验原始 MP4，再把视频关键帧和结构化元数据交给既有 Codex CLI 会话生成一条简短回复并走原发送队列。

## 已验证事实

- 拼多多商家版 1.0.19 的客户视频可由 AX 暴露为客户消息内的视频标记，或“时长文本覆盖在缩略图上”的降级形态。
- 自动点击视频后，CEF `Cache/Cache_Data` 的新增或更新记录包含拼多多 HTTPS 视频地址。
- 本机真实测试已用该地址取得 HTTP 200 的有效 MP4：8.2 秒、720×1280、H.264/AAC。
- 正式程序当前只通过 Codex CLI 的 `-i` 参数提交图片；MP4 不能直接作为该参数的视觉附件。

## 识别和下载

新增 `video` 消息类型。客户 `onemsg` 内满足以下任一条件即识别为视频：明确视频 DOM 类；或同一消息内存在合法时长文本和可点击缩略图。客服消息、普通图片、视口外节点和不完整 AX 树不能成为自动点击目标。

处理新视频时先快照所有 CEF profile 的缓存目录，再点击与该 `messageID` 对应的客户视频，随后只检查基线之后新增或改变的缓存文件。地址必须是 HTTPS、拼多多允许域名，并带 MP4 路径或视频 MIME 证据。下载接受 HTTP 200/206；文件必须有 ISO BMFF 文件头、有效时长和视频轨道。临时签名地址只在内存使用，不写日志和持久化状态。

所有打开、等待缓存和恢复聊天界面的动作都持有当前 `UIOperationLease`。租约失效立即停止当前 UI 操作，避免点到其他客户。附件按 `uid/messageID` 保存，并用 SHA-256 防止重复处理。

## Codex 输入

新增视频附件模型，保存消息 ID、本地 MP4、SHA-256、时长、尺寸、编码、带时间戳关键帧和可选语音转写。AVFoundation 从视频头部、中段和尾部最多提取 6 张 JPEG；近似重复帧可以跳过。关键帧通过现有 Codex `-i` 图片通道提交，prompt 中使用 `<chat_video_attachments>` 描述它们来自哪条视频及对应时间点。

若音频转写能力不可用或失败，附件仍然有效，并明确标记“未取得语音内容”；不能因为转写失败阻塞视频画面回复。不得把 MP4 路径伪装成 `-i` 图片参数。

## 调度和故障策略

视频附件属于冻结客户批次并随任务持久化，历史续接按照视频 SHA-256 去重。只有当前批次包含的新客户视频才触发下载，旧历史和客服视频不会重新处理。

视频识别、点击、地址发现、下载、校验或关键帧提取任一失败时，仍保留 `[视频]` 消息并继续排队生成。诊断信息进入本地状态，但 prompt 只告诉 Codex“视频内容暂未读取成功，请简短询问客户要查看什么”，不能让单个视频任务阻塞其他用户。

## 进度与安全

UI 显示视频识别、打开、捕获链接、下载、解析、生成和发送阶段。真实发送继续使用既有发送器、PDD 会话标识、消息 ID 去重和任务隔离，不引入 GZC 标识。自动化不操作订单，不记录签名 URL，不使用 OCR 判断播放状态，也不录屏。

## 验证

自动测试覆盖：AX 视频与普通图片区分、缓存增量选择、下载校验、关键帧生成、模型兼容解码、prompt 视频段、Codex 图片参数、历史续接去重，以及视频处理失败仍生成回复。最后运行全量 `swift test`、release 构建，并用当前拼多多真实视频验证“识别→打开→下载→关键帧→Codex 草稿”的链路；真实对外发送沿用正式自动客服开关。
