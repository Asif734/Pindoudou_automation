# 拼多多 AX 主读、OCR 兜底设计

日期：2026-09-02

## 背景与根因

当前生产链路在 `PDDAXConversationDriver.capture` 中无条件执行整页 OCR，随后调用 `mergeOCRAuthoritative`。AX 只补充尾部图片和顺序。这与 2026-08-29 设计稿规定的“AX 发送方、消息 ID 和时间优先”相反。

2026-09-02 的真实状态显示，OCR 把右侧客服回复和斜向店铺水印识别成客户消息，并因每轮文字略有差异生成新 `ocr-*` ID。程序因此形成“自动回复 → OCR 当成新客户消息 → 再生成回复”的反馈循环。受影响的 `GZC-000001` 历史已增长到 237 条、客户游标 112，不能继续作为新链路的可信前缀。

## 目标

1. AX 可用且包含结构化消息时，AX 是文字、发送方、类型、消息 ID、时间和顺序的唯一权威来源。
2. AX 明确缺失或在未读证据存在时短时不前进，OCR 只补最末端新客户文本，不再导入整页历史。
3. AX 恢复后，用 AX 消息吸收 OCR 临时消息，保证同一客户内容不回复两次。
4. 单个数据源失败只影响当前捕获，不停止其他用户和后续轮询。
5. 旧 OCR 污染历史保留作审计，但不得进入新时间线、Prompt 或回复队列。

## 非目标

- 不修改拼多多水印设置。
- 不恢复“整页 OCR 是聊天历史权威”的旧行为。
- 不改变 Codex 模型、知识库检索、短回复 Prompt 或 AX 发送器。
- 不用 OCR 发现会话或点击发送。

## AX 权威快照

新增 `PDDAXVisibleMessageEvidence`，遍历当前聊天面板全部可见 `onemsg` 节点并记录：

- `messageNodeCount`
- 成功解析的 `[PDDChatMessage]`
- 解析失败诊断
- 由可见消息 ID、发送方、类型和规范化正文构成的 fingerprint

`PDDChatParser` 继续按 DOM class 判定：`buyer-item` 为客户、`cs-item` 为客服、`image-msg` 为图片。带 `middlePanel_list_*` 的 DOM ID 继续作为稳定消息 ID。

AX 快照满足以下条件才是结构有效：聊天输入框存在；至少存在一个 `onemsg`；至少一条消息成功解析；同一节点不能同时含 `buyer-item` 与 `cs-item`。如果当前会话真实为空，可由单独的空会话标记表示，不能用“零消息节点”猜测为空。

## AX 明显失效的判据

任一条件成立即允许 OCR 兜底：

1. 聊天面板或 `onemsg` 子树缺失。
2. 存在未读红点证据，但在 1 秒截止时间内取得至少 3 次 AX 快照（相邻采样至少间隔 200ms），fingerprint 始终不变，且没有出现新的客户 DOM ID。
3. 当前 AX 快照相对同一 UID 的上次可信快照发生结构回退：消息节点全部消失、可解析数归零，或可见稳定 ID 的顺序倒退。

AX 通知不作为必要条件；历史实测新消息可在约 0.536 秒进入 AX tree，但不产生有效通知，因此 200ms 调度兜底仍保留。

## OCR 兜底范围

OCR 兜底仍使用本地 ScreenCaptureKit 和 PaddleOCR，但不把解析出的整页消息交给 `PerUserChatStore`。

1. 用最后一条 AX 可见消息作为锚点；只考虑锚点下方的 OCR 气泡。
2. 有锚点时，只保留锚点之后最底部、位于客户侧的连续文本气泡。
3. 无锚点但存在未读红点时，只保留画面最底部一个客户侧文本气泡。
4. 丢弃与任一可见 AX 客服消息规范化正文完全相同的 OCR 文本；不使用模糊相似度改写或猜测正文。
5. 丢弃输入框、工具栏、时间、店铺/客服名称和已知平台噪声；`复制` 末尾清理规则继续生效。
6. OCR 不能证明存在新尾部客户文本时，本轮不创建任务，下一轮继续扫描；不得回退为整页导入。

## 临时消息与 AX 回收

OCR 兜底产生 `ocr-provisional-*` 消息，并为每个 UID 持久化 receipt：规范化正文、可选时间、首次观察时间、回复状态和对应任务 ID。

- receipt 未回复时可进入冻结批次。
- receipt 已回复后，后续 AX 客户消息若规范化正文完全相同，并且 AX 消息首次出现时间不晚于 receipt 首次观察后 30 秒，则标记为同一消息并吸收，不再次推进可回复事件。
- 正文不同或超过 30 秒窗口的 AX 客户消息视为真正的新消息。
- receipt 只用于去重，不允许覆盖 AX 的发送方、类型、DOM ID 或正文。

## 新历史与旧状态迁移

引入 AX-first 历史代际，避免旧 `history.jsonl` 的 OCR 污染继续成为游标前缀：

1. 旧历史文件原样保留，不删除、不改写。
2. 新链路写入独立的 AX-first 历史文件；第一次看到每个 UID 时用可信 AX 快照建立 baseline。
3. 启动迁移时，旧链路尚未发送的 `ocr-*` 任务标记为“AX-first 迁移丢弃旧 OCR 待处理任务”；已完成/已失败记录保留。
4. 清空旧 pending capture requests，不复用旧 OCR answered cursor。
5. 若迁移时该会话仍有未读红点，则 baseline 到最后一条 AX 客服消息，并允许其后的 AX 客户尾部立即形成任务；没有未读证据则只建立 baseline，避免重发历史。

迁移必须幂等；重复启动不能重复归档或重新回复 baseline 内容。

## 捕获流程

```text
打开并核对 UID
  → 读取 AX 权威快照
  → AX 有新客户消息：只合并 AX，创建/推进批次
  → AX 无新消息且无失效证据：结束本轮
  → AX 明显失效：运行尾部 OCR
  → OCR 有可信最末端客户文本：写 provisional receipt 并创建批次
  → 后续 AX 恢复：吸收 provisional，继续使用 AX 时间线
```

图片仍由 AX `image-msg` 处理；OCR 不创建图片消息。

## 运行状态与诊断

界面和事件日志明确显示当前来源：

- `AX 权威读取：N 条可见消息`
- `AX 未前进（3/3），启用尾部 OCR`
- `OCR 临时客户消息：<摘要>`
- `AX 已恢复并吸收 OCR 临时消息`
- `AX/OCR 均无可信新消息，继续轮询`

不得继续使用笼统的“OCR 已读取 N 条可见气泡”来暗示这些气泡全部进入历史。

## 测试与验收

### 单元测试

- AX 有结构化文字时完全忽略 OCR 对发送方和正文的冲突判断。
- AX 客服气泡绝不因 OCR 左右误判进入客户时间线。
- 未读证据 + 3 次 AX fingerprint 不变才启用 OCR；前两次不启用。
- OCR 只取 AX 锚点后的最底部客户尾部，不导入旧客服回复和水印。
- AX 恢复后吸收已回复 provisional，不重复创建任务。
- AX 恢复后不同的新客户消息仍进入下一批。
- 迁移保留旧文件和终态任务，丢弃旧非终态 OCR 任务，并且重复执行结果不变。
- AX 子树缺失、OCR 失败和恢复过程不造成调度器全局停止。

### 真实验证

1. 在当前拼多多会话做只读 AX/OCR 对照，确认 `buyer-item`/`cs-item` 与界面方向一致。
2. 发送一条唯一测试文本，记录画面出现、AX 首次出现、是否调用 OCR、任务创建和最终回复时间。
3. 人为使用旧 AX 快照模拟停滞，确认只生成一个 provisional 任务。
4. AX 恢复后确认没有第二次回复。
5. 全量 Swift 测试、Release 构建、App 资源和签名检查通过后，重新启动候选版正式模式。
