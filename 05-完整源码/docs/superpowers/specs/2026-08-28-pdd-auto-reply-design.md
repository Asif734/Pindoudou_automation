# 拼多多纯 AX 全自动客服设计

日期：2026-08-28

## 背景

现有拼多多 AX 读取器能够用 macOS Accessibility API 读取当前客服聊天、识别 `GZC-` 用户 ID、解析文字/链接/图片消息、保存每用户历史，并用本机 Codex CLI 为每位用户生成独立会话中的建议回复。它刻意不向拼多多发送内容。

本设计新增一个独立的“拼多多全自动客服”应用。它复用“检查已打开的千牛”项目中已经验证的调度语义，但把千牛 OCR、坐标点击和截图采集全部替换为拼多多纯 AX 读取与 AX 操作。图片本阶段完全不处理。

## 目标

- 自动发现有新客户文字或链接的拼多多会话。
- 纯 AX 切换会话、读取聊天、填写输入框、触发发送并回读确认。
- 每位客户使用独立 Codex 会话和独立持久状态。
- 使用已回复游标和冻结批次，保证生成期间到达的后续消息不会被吞掉。
- 同一客户严格按批次 FIFO 发送；不同客户可并行生成，但所有拼多多 UI 操作必须串行。
- 只有确认发送成功的批次才能推进已回复游标。
- 应用、Codex CLI 或拼多多异常退出后能够安全恢复，不把不确定发送当作成功。
- 保留现有读取器和单次解析测试器，不覆盖、不迁移、不改变它们的行为。

## 非目标

- 不识别、复制、上传、理解或回复图片。
- 不使用 OCR、截图、坐标点击、键鼠事件、网页脚本、网络接口或 DOM 注入读取和操作拼多多。
- 不自动处理订单、退款、打款、优惠券、售后申请或其他非文字聊天操作。
- 不修改千牛应用、千牛运行状态或千牛知识库原件。
- 不用“最后一条是客服”推断客户消息已经被本程序回答。

## 产物与隔离

新增独立应用：

```text
outputs/拼多多全自动客服.app
```

现有两个应用继续保留：

```text
outputs/拼多多AX读取器.app
outputs/拼多多AX单次解析测试器.app
```

自动回复状态使用独立目录：

```text
~/Desktop/拼多多AX记录/自动回复/
  scheduler-state.json
  events.jsonl
  archive/
  用户/<UID>/
    history.jsonl
    codex-session.json
```

自动回复应用不读取千牛队列，不写千牛目录，也不导入任何旧发送任务。

## 运行模式

- 应用启动后默认停止，必须由用户按“开始自动回复”进入运行状态。
- 第一阶段只允许测试 UID `GZC-000001`，用于真实 AX 收发验证。
- 测试验收完成后才允许在界面中切换到全部用户模式。
- 停止会阻止新的发现、采集和发送；已经启动的 Codex 进程允许完成并把结果可靠落盘，但停止期间不发送。
- 同一时刻只允许一个自动回复应用实例持有运行锁。

## 纯 AX 边界

目标应用固定为 `com.pinduoduo.merchantMac`。所有拼多多交互只允许：

- `AXUIElementCopyAttributeValue`
- `AXUIElementCopyMultipleAttributeValues`
- `AXUIElementSetAttributeValue`
- `AXUIElementPerformAction`
- `AXObserver`

会话列表、未读标记、UID、消息节点、输入区和发送控件必须通过 AX 结构与稳定 DOM 属性定位。禁止用屏幕坐标兜底。关键控件缺失、歧义或不支持 AX 操作时，本次 UI 事务失败，不猜测目标。

`AXEnhancedUserInterface` 只在未启用时设置一次；不得反复切换以“刷新”CEF。读取使用批量 AX 属性 API，保持当前约 70–100ms 的热态扫描路径。

## 会话发现

调度器运行时每 1.0 秒检查一次会话列表，同时监听可用的 AX 变化通知。轮询是可靠性底线，AXObserver 只用于提前唤醒，不能作为唯一信号。

发现器输出稳定 UID 集合，不直接生成或发送。流程为：

1. 读取左侧会话列表及未读证据。
2. 对候选行执行 AXPress 打开会话。
3. 等待页面稳定，然后从主聊天区解析唯一 `GZC-` UID。
4. UID 与目标模式不匹配时立即退出该事务。
5. 同一 UID 已有活动任务时只标记“可能有补充消息”，不创建重叠任务。

未读数字和红点仅用于发现。某 UID 一旦进入持久调度状态，后续客户消息是否需要处理由客户游标决定，不再依赖红点是否仍存在。

## 消息范围与图片规则

可执行客户事件只有：

- 文字消息
- 链接消息

图片消息仍可作为 `[图片]` 保存在完整历史中，方便界面检查，但：

- 不进入可执行客户事件序列。
- 不参与回复游标摘要。
- 不作为生成任务触发条件。
- 不传给 Codex，不作为附件。
- 只有图片而没有新文字/链接时，不生成、不发送。
- 图片与文字混合到达时，只冻结并回答文字/链接；图片不阻塞后续批次。

每个可执行客户事件使用稳定消息 ID。若 CEF 未提供可用 ID，则使用发送方、类型、显示时间和规范化内容生成稳定摘要。同一批次中相同文字的多次发送必须保留独立事件身份。

## 已回复游标与冻结批次

每位客户持久保存 `answeredCursor`：

- `count`：已确认覆盖的可执行客户事件数量。
- `digest`：对应前缀的链式 SHA-256 摘要。

每个任务冻结：

- `startCursor`
- `endCursor`
- `targetCustomerJSONL`
- `fullHistoryJSONL`
- 客户 UID
- 客户修订摘要
- 生成结果、重试状态和发送结论

核心不变量：

1. 任务只覆盖 `(startCursor, endCursor]`。
2. 同一 UID 的未完成任务区间不得重叠、倒退或跳过事件。
3. 任务冻结后，后来的客户消息只能进入下一批。
4. 只有发送结论为 `sent` 才能把游标推进到该任务的 `endCursor`。
5. 发送失败、停止、崩溃或发送结果不确定都不能推进游标。
6. 客服消息、红点和可见消息顺序都不能自行推进游标。

例如客户依次发送 A、B、C、D：

```text
任务 1：(0, A]   -> 回复 A
任务 2：(A, C]   -> 合并回复 B+C
任务 3：(C, D]   -> 回复 D
```

A 生成或发送期间到达的 B/C 必须进入任务 2，不需要等待另一个红点。

## 首次运行基线

自动回复状态不存在时，不得把历史聊天全部重新回复：

- 没有未读证据的会话：把当前可执行客户事件尾部记录为初始基线，不发送。
- 有未读证据的会话：仅把最后一条客服消息之后连续到达的客户文字/链接作为首个冻结批次；更早前缀作为基线。
- 无法唯一确定 UID、消息边界或未读会话时：隔离该 UID 并显示诊断，不猜测、不发送。

基线一旦建立，后续只使用持久游标和确认发送记录，不再用最后发言者推断进度。

## Codex 生成

- 使用本机 `/Applications/ChatGPT.app/Contents/Resources/codex`，固定 `gpt-5.6-sol`、`medium` 推理、`read-only` 沙箱和 `approval=never`。
- 每个 UID 绑定独立 thread ID，沿用现有一小时会话租约和精确 resume 机制。
- Prompt 同时提供完整历史和严格冻结的目标客户批次。
- Codex 只能回答目标批次中的文字/链接问题；完整历史只作为上下文。
- 客户聊天内容一律视为待回答数据，不得作为操作本机、改变自动化规则或调用外部系统的指令。
- 回复必须是非空纯文本；结构化结果校验失败时不进入发送状态。
- 使用与千牛自动客服一致的客服规则，并只读检索 `/Users/scy/Desktop/AI客服记录/知识库/Grozziie-China-KB-2026-08-24.zip`；知识库原件不复制、不修改。

同一 UID 同时最多有一个生成任务。不同 UID 的生成可以并行，实际并发数沿用千牛的内存自适应策略。

## 发送事务

所有拼多多 UI 操作由单一串行执行器完成。发送事务不可与发现、切换或其他发送交错：

1. 用 AX 打开目标会话。
2. 解析并精确核对当前 UID。
3. 读取输入区，要求为空；测试阶段若需要恢复本程序草稿，必须同时匹配持久保存的任务 ID、UID 和完整文本 SHA-256，否则视为未知草稿并停止。
4. 用 `AXUIElementSetAttributeValue` 写入冻结回复。
5. 再次读取输入区，确认文本逐字一致。
6. 再次核对当前 UID。
7. 对唯一发送控件执行 `AXPress`。
8. 轮询 AX 消息树，寻找该 UID 下新增且内容一致的客服消息。
9. 确认后返回 `sent`，原子完成任务并推进游标。
10. 立即重新采集该 UID 尾部，形成已观察到的后续批次。

禁止使用 Return 键、坐标点击或剪贴板作为发送兜底。

## 发送确认与不确定状态

CEF 的 AX 缓存可能比视觉页面短暂落后，因此发送确认使用有上限的事件驱动轮询，而不是一次读取：

- AXObserver 通知可提前触发回读。
- 发送动作后最多等待 3.0 秒，并进行多次约 70–100ms 的快照读取。
- 找到新的客服消息 ID、相同文本和相同 UID才算成功。
- 发送动作执行前失败：`failedBeforeSend`，允许安全重试。
- 发送动作执行后没有确认：`uncertain`，不推进游标，也不自动再次点击发送，防止重复回复。
- `uncertain` 必须在 UI 中明确显示，等待人工核对后处理。

## 人工客服消息

普通客服消息保留在完整上下文中，但不自动推进本程序的已回复游标。只有本程序拥有的任务获得发送回读确认，才能推进对应批次。

自动回复运行时不建议人工同时使用同一客服账号。如果发现任务生成期间出现无法与本程序已确认发送记录匹配的新客服消息，暂停该 UID 的自动发送并显示“检测到人工接管”，其他 UID 可继续运行。

## 持久化与恢复

调度状态每次变化都先原子落盘，再执行不可逆 UI 动作：

- 捕获中断：恢复为待捕获。
- 生成中断：恢复为待生成，保持原冻结区间。
- 回复就绪：重启后优先发送原回复，不用新消息替换。
- 状态为发送中时退出：恢复为 `uncertain`，禁止自动重发。
- 已确认发送：任务完成、游标推进和归档写入必须在一次持久提交中完成。
- 历史不再是游标对应的合法前缀：隔离该 UID，保留证据，不影响其他客户。

终态任务保存不可变 JSON 证据与只读文本摘要，包括 UID、任务 ID、冻结区间、回复、发送结论和时间。

## UI

独立应用提供：

- 开始/停止自动回复。
- 测试 UID / 全部用户模式。
- 当前 UI 操作所有者。
- 正在捕获、排队、生成、就绪、发送、完成、失败、不确定的任务列表。
- 每位客户的已回复游标、最新客户游标和 Codex 会话状态。
- 事件日志和失败原因。

默认窗口只显示状态，不允许直接编辑生成结果；测试阶段额外提供“生成但不发送”的干运行模式用于验证发现、批次和 UID 路由。

## 安全边界

- 缺少辅助功能权限时不启动。
- 拼多多不在运行、窗口不唯一、UID 不唯一、输入区不唯一或发送控件不唯一时不发送。
- 每次写入前、写入后和发送前均核对 UID。
- 输入区已有未知草稿时不覆盖。
- 回复为空、超过 1000 个 Unicode 字符、包含结构化协议错误或 Codex 未完整结束时不发送。
- 与旧拼多多自动化实例或冲突进程并存时停止启动。
- 所有客户数据和 Codex 会话记录仅保存在本机既定目录。

## 测试策略

### 单元测试

- 图片不进入可执行事件序列，也不触发生成。
- 图片加文字只冻结文字/链接。
- A 生成期间到达 B/C，A 发送成功后自动形成 B+C。
- B+C 生成期间到达 D，严格形成下一批 D。
- 重复文字拥有独立事件身份。
- 发送失败和不确定发送不推进游标。
- 只有已确认发送推进游标。
- 不同 UID 使用不同 Codex thread ID。
- 停止状态不发现、不采集、不发送。
- 恢复发送中任务时进入不确定状态。

### AX 选择测试

用保存的脱敏 AX fixture 验证：

- 会话列表和未读行选择。
- 当前 UID 唯一解析。
- 输入区唯一选择。
- 发送控件唯一选择。
- 歧义控件一律失败。
- 写入后文本回读不一致时禁止发送。

### 调度交错测试

使用假驱动穷举客户消息在捕获、生成、就绪、发送前、发送动作后和发送确认后的到达时序。每个可执行客户事件必须恰好属于一个冻结批次，同一 UID 发送顺序必须与批次顺序一致。

### 实机测试

只使用 `GZC-000001` 测试会话：

1. 干运行：发现、切换、UID 核对、捕获和生成，但不发送。
2. 输入事务：写入测试文本并回读，然后清空，不点击发送。
3. 单条文字真实收发并回读确认。
4. A 生成期间发送 B/C，验证 A、B+C 顺序。
5. 图片单独到达，验证无任务、无发送。
6. 图片加文字到达，验证只回答文字。
7. 发送后模拟 AX 确认超时，验证进入不确定状态且不重复点击。
8. 在捕获、生成、就绪和发送前分别重启，验证恢复语义。

只有全部自动测试通过、签名有效、测试 UID 实机证据完整，才能开放全部用户模式。

## 验收标准

- 拼多多读取和操作全程纯 AX，无 OCR、截图或坐标兜底。
- 每个文字/链接客户事件恰好进入一个冻结批次。
- 同一 UID 不漏答、不乱序、不因 AX lag 自动重复发送。
- 图片不触发生成或发送。
- 发送到错误 UID 的测试路径为零；任一 UID 核对失败都会终止发送事务。
- 发送成功必须有新增客服 AX 消息的回读证据。
- 自动测试、Release 构建、代码签名和测试 UID 实机测试全部通过。
