# PDD AX 延迟离群样本调查

日期：2026-08-30  
范围：历史自动回复归档、持久化任务状态、AX 通知事件，以及 2026-08-30 的受控实时探针。

## 结论

历史字段 `capturedAt - middlePanel_list_<epoch-ms>` 不是纯 AX tree lag。`capturedAt` 是程序把消息合并进历史的时间，期间可能包含任务占用、通知缺失、调度等待、发送确认门禁和应用未运行。因此旧统计只能作为“程序首次保存延迟”的上限。

五个离群值中：

- 653 秒：确定是旧任务发送确认/游标对账阻塞，不是 AX tree lag。
- 69 秒：高度可能是前序任务进入旧阻塞状态后，当前 UID 未及时重新捕获；不是纯 AX 证据。
- 35 秒与 12.568 秒：同一次批量捕获，发生在前序发送任务和重试期间；主要是调度/任务串行等待，不能归因于 AX tree。
- 11.25 秒：发生在前序阻塞任务期间，同时存在 17 秒 AX 通知空窗；可能是 tree 批量刷新，也可能是没有及时重扫，现有记录无法二分。

2026-08-30 的受控探针给出正常样本：图片消息 ID 对应发送时间 09:43:31.360，首次在 AX 子树发现时间 09:43:31.896，延迟上限 536ms；消息子树扫描耗时 87ms，但没有收到有效 AX 通知。

## 数据解释限制

消息 ID `middlePanel_list_<数字>` 的数字是消息生成的 Unix 毫秒时间。历史 `capturedAt` 精度常被写成整秒，存在约 1 秒量化误差。归档没有保存每一次“扫描但未发现消息”的负结果，也没有同时保存像素首次出现时间，因此不能从归档直接证明 AX tree 在整个差值期间都没有该节点。

## 逐条还原

### 11.25 秒：`你好`

- ID：`middlePanel_list_1787916427750`
- 发送：17:27:07.750
- 首次保存：17:27:19.000
- 差值：11.250 秒
- 同一阶段前一条客户消息 `大家都变得不` 在 17:27:02.811 发送、17:27:03.000 保存，仅 0.189 秒。
- 17:27:07.750、17:27:11.146、17:27:13.899、17:27:15.606 的四条消息一起在 17:27:19 保存，表现为批量可见或批量捕获。
- AX 通知事件从 17:27:03.072 到 17:27:20.155 存在约 17 秒空窗。
- 前序任务 sequence 16 后来被标记为“旧阻塞状态”；sequence 17 又因“输入区存在未知草稿”失败；sequence 18 才最终处理这组消息。

判断：不是一个干净的 tree-lag 样本。它同时受到前序任务阻塞和通知空窗影响。不能排除 PDD 一次性刷新四个 AX 节点，但也不能证明节点在 17:27:19 前不存在。

### 12.568 秒：`说的话v的`

- ID：`middlePanel_list_1787901515432`
- 发送：13:18:35.432
- 首次保存：13:18:48.000
- 差值：12.568 秒
- 与 35 秒样本在同一批次中冻结。
- sequence 3 包含三条重叠客户消息并记录 6 次任务重试；sequence 4 又冻结扩展后的同一前缀并记录 4 次重试。
- 前序自动回复在 13:18:26.615 已经出现在聊天里，但相关任务直到 13:30:42 才统一完成 delivery reconciliation。

判断：这是旧调度器在活动任务、重叠批次和发送确认未及时推进游标时的等待，不是纯 AX tree lag。

### 35.023 秒：`对很多很多话`

- ID：`middlePanel_list_1787901492977`
- 发送：13:18:12.977
- 首次保存：13:18:48.000
- 差值：35.023 秒
- 同组第一条 `时间还不睡` 在 13:18:06.367 发送、13:18:07.000 保存，仅 0.633 秒。
- 13:18:26.615 出现客服自动回复，随后 13:18:35.432 又有客户消息；两条客户消息直到 13:18:48 一起进入下一捕获。
- sequence 2/3/4 是相互重叠的批次；sequence 2 最终成为旧阻塞状态，sequence 3/4 分别重试 6/4 次。

判断：差值跨越了前一任务的生成、发送、确认与下一轮冻结过程。它测到的是“端到端调度等待”，不能证明 AX tree 慢了 35 秒。

### 69.084 秒：`的海上搜救`

- ID：`middlePanel_list_1787904158916`
- 发送：14:02:38.916
- 首次保存：14:03:48.000
- 差值：69.084 秒
- 前一条客户消息 `单家独户的吧` 在 14:02:30.638 发送、14:02:34.000 保存，仅约 3.36 秒，并创建 sequence 6。
- sequence 6 已经生成回复，但没有 confirmed service ID，后来被迁移为“旧阻塞状态已解除；已跳过当前批次并继续”。
- 14:03:07.836 出现客服 `1`，它与目标客户消息同样到 14:03:48 才进入保存历史。
- sequence 7 在捕获后处理目标，最终回复时间为 14:06:33.332。

判断：高度符合“前序 sequence 6 占用/阻塞当前 UID，后续消息直到重新捕获才进入 sequence 7”。69 秒不是可归因于 AX tree 的独立测量。

### 653.214 秒：`16-6等于？`

- ID：`middlePanel_list_1787901588786`
- 发送：13:19:48.786
- 首次保存：13:30:42.000
- 差值：653.214 秒
- sequence 1/3/4 对应的客服回复实际上分别在 13:18:26.615、13:19:39.288、13:19:50.595 已出现在聊天中。
- 但三个任务都到 13:30:42.978 才同时产生 `delivery-reconciled` 事件并完成归档。
- sequence 3/4 分别记录 6/4 次重试。
- 目标消息在对账完成的同一秒进入 sequence 5；13:30:50.298 已回复 `16-6等于10。`。

判断：确定是发送后 AX 回读/任务游标没有及时对账，导致当前 UID 后续批次被旧门禁压住约 11 分钟。消息一旦获准进入 sequence 5，8 秒内即完成回复。653 秒不应计入 AX tree lag。

## 根因分类

1. 旧调度器对同一 UID 的任务串行化，活动或阻塞任务会推迟新批次捕获。
2. 发送已真实出现在页面，但 AX 回读确认没有及时把任务标成 completed、推进 answered cursor。
3. 历史的 `uncertain`、`quarantined` 和未知草稿门禁会停止或延后该 UID。
4. PDD 的 app-level AX 通知噪声很大，而真实新消息可能完全没有有效通知。
5. 归档只保存成功捕获时间，没有保存像素出现时间和每次空扫描，因此不能把所有端到端差值解释为 AX tree lag。

## 目前可以支持的判断

现有证据支持“PDD AX/CEF 有偶发缺树和通知不可靠”，但不支持“这些 11/13/35/69/653 秒全部是消息从画面出现到 AX tree 更新的延迟”。五个样本里，653 秒确定是调度阻塞；69、35、13 秒主要由旧任务状态和串行调度解释；11 秒仍可能含真实 AX tree 批量刷新，但证据不足。
